# 电商平台 + 退赔决策系统 · 完整需求文档

> 在工单1「客诉舆情退赔决策系统」基础上，新增**买家侧电商前台**（注册/逛/买/售后）+ **订单三查校验** + **挂起上下文 Redis 快照**三大增强
>
> 版本：v2.0 ｜ 日期：2026-08-31 ｜ 状态：待实施

---

## 1. 背景与目标

### 1.1 需求来源

1. **评审建议**：退赔决策 Agent 应对「订单真实性 / 商品一致性 / 价格一致性」做判断，体现退款状态管理与三态流转（Running → Suspended → Completed），挂起时通过 Redis 序列化保存图上下文。
2. **业务扩展**：在工单1 基础上新增商品浏览、购物车、下单、售后入口，完善成功能齐全的电商平台。

### 1.2 目标

在不推翻工单1 现有决策流的前提下：

- **补「订单校验」**：决策流最前面加一道硬闸，用真实订单数据做三查，堵住「伪造订单 / 偷换商品 / 虚报金额」的资损漏洞。
- **补「挂起上下文 Redis 快照」**：保持 PostgreSQL 最终真相不变，挂起时把图上下文序列化到 Redis，满足要求并加速读取。
- **加「电商前台」**：让系统能自己「造真实订单」，把 `RefundCase.order_id` 从游离字符串变成真关联，全链路闭环。

## 2. 现状摸底（关键事实）

| 维度 | 现状 | 落差 |
| --- | --- | --- |
| 订单三查 | **完全没有**，`RefundCase.order_id` 是游离字符串，系统无订单数据源 | 缺整块能力 |
| 三态流转 | 已实现（`interrupt` 挂起 / `finalize` 落终态），但淹没在八态里 | 已实现但「体现」不够 |
| 挂起上下文存储 | 现在存 PostgreSQL（`PostgresSaver`，注释「金融级不丢失」） | 与「Redis 序列化」要求不符 |
| 买家侧 | 无 Customer 表，`User.role` 只有 CSR/MANAGER/ADMIN，无买家 | 缺整块前台 |

**技术栈**：后端 FastAPI + SQLAlchemy + PostgreSQL + Redis Streams 异步 Worker；前端 React 18 + TS + Vite。

**金额硬约束**：金额一律「分」（整数 BIGINT），禁止浮点。退赔是资损敏感场景，宁可慢不能丢。

## 4. 全链路闭环总览

```
买家注册/登录（Customer 表，手机号+密码）
        ↓
逛商品（商品列表/详情，小米真实数据）
        ↓
加购物车 → 结算下单 → 模拟支付
        ↓
自动记录订单落库（Order + OrderItem 快照）
        ↓
「我的订单」点某笔订单 → 申请售后（自动带出 order_no + 实付金额）
        ↓
create_case（复用现有接口，鉴权放开 BUYER）
        ↓
order_verify 三查核对（真实性/一致性/价格 + 防重复退款）
        ↓ 通过
凭证 → 风控 → 舆情 → 决策（evidence → fraud → sentiment → decision）
        ↓ 退款通过
finalize 回写订单状态（Order.status = REFUNDED）
        ↓
买家「我的订单」看到售后状态标签
```

## 5. 架构决策（A~F）

| # | 决策点 | 定案 |
| --- | --- | --- |
| A | 后端模块 | `app/api/` 下加 customer_auth.py / products.py / cart.py / orders.py（并排现有 cases.py） |
| B | 前端路由 | `/buyer/*` 子路由复用现有 React 项目（RequireBuyerAuth 守卫） |
| C | 鉴权分离 | JWT payload 加 `type=STAFF/BUYER`；后端加 `require_buyer` / `require_staff` |
| D | 支付模拟 | `/orders/{id}/pay` 同步改状态（PENDING_PAYMENT→PAID），零延迟同事务 |
| E | 回写路径 | finalize_node 同步 ORM 写回 Order.status（与 checkpoint 同事务，防劈叉） |
| F | 状态机位置 | OrderStatus enum 写进现有 domain/models.py（与 CaseStatus 并排） |

**关键权衡**：
- E 选**同步写死**而非 Redis 事件解耦 —— 退赔资损敏感，宁可耦合不可劈叉（钱退了订单没标记）。
- D 选**同步**不模拟异步回调 —— MVP 目标是测退赔流，支付非核心，接口签名不变、真接入时换实现即可。

## 6. 数据模型（5 张表 + 8 态状态机）

### 6.1 五张表

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| **Customer** | id · phone(UNIQUE) · password_hash · nickname(NULL) · created_at | 买家 |
| **Product** | id · product_id(UNIQUE 小米ID) · name · price_cents · description · category · image_url(NULL) · is_active | 商品 |
| **CartItem** | id · customer_id(FK) · product_id(FK) · quantity · created_at · 联合唯一(customer_id, product_id) | 购物车 |
| **Order** | id · order_no(UNIQUE) · customer_id(FK) · total_cents(下单锁定) · status · created_at/paid_at/refunded_at | 订单 |
| **OrderItem** | id · order_id(FK) · product_id(弱关联) · product_name(快照) · price_cents(快照) · quantity · subtotal_cents | 明细快照 |

金额一律「分」（BIGINT）。密码用标准库 PBKDF2 哈希（与现有 User 表一致）。

### 6.2 订单状态机（8 态）

```
下单        支付        发货        收货
PENDING_PAYMENT → PAID → SHIPPED → COMPLETED
                   ↘
                 售后触发
                 REFUNDING → REFUNDED   (退款)
                 EXCHANGING → 换货      (换货)
                 CLOSED                (取消/超时)
```

### 6.3 数据模型待商量点（Q1~Q5）

| # | 决策点 | 定案 |
| --- | --- | --- |
| Q1 | order_no 规则 | 时间戳 + 6 位随机（不用纯自增，防暴露订单量） |
| Q2 | SHIPPED/COMPLETED 触发 | 运营后台一键「发货」+ 买家一键「确认收货」（支付只到 PAID） |
| Q3 | OrderItem.product_id | 弱关联（字符串，不建 FK），对账靠快照 name+price |
| Q4 | Customer.nickname | 要，注册时可空 |
| Q5 | 换货状态 | 独立 EXCHANGING 态（与 REFUNDING 并行） |

### 6.4 鉴权改造（C1 落地）

- `create_access_token` 加 `type=STAFF/BUYER` claim。
- 新增 `get_current_customer` 依赖，查 Customer 表。
- 现有 `get_current_user` 加 type 校验（只认 STAFF）。

## 7. order_verify 三查实现

### 7.1 三查逻辑

| 校验项 | 查什么 | 判定逻辑 | 失败处理 |
| --- | --- | --- | --- |
| **订单真实性** | Order 表按 order_no 查 | 查不到 → 订单不存在 | **REJECT**（伪造订单，直接拒） |
| **商品一致性** | OrderItem 明细 | 订单无明细 / 快照残缺 → 不一致 | **HUMAN_REVIEW**（转人工） |
| **价格一致性** | 三层对账 | ① 申报额 ≤ 实付额（已有 D-012）② 实付额 = Order.total_cents ③ Σ(单价×数量) = 总额 | **HUMAN_REVIEW**（转人工） |

### 7.2 MVP 范围约定

- 工单1 的 `RefundCase` 无「退款商品」字段，「描述↔商品字面匹配」需 NLP，**MVP 不做**。
- MVP 的商品一致性 = **订单明细存在且完整**；字面匹配留 LLM 后续补。

### 7.3 决策流改造

```
改造前：intake → evidence → fraud → sentiment → decision
改造后：intake →【order_verify 三查】→ evidence → fraud → sentiment → decision
```

- state 新增：`order_exists` / `product_matched` / `price_matched` / `order_verify_reason`
- 新增 `order_verify_node`（`@record_agent_run("ORDER_VERIFY")`）+ `OrderVerifyProvider`
- decision.py `decide()` 最前面插 3 条：订单不真实→REJECT；商品/价格不一致→HUMAN_REVIEW

## 8. 防重复退款（订单状态校验）

同一订单只能售后一次。`order_verify` 顺带查 `Order.status`：

```
Order.status ∈ {REFUNDED, REFUNDING, EXCHANGING, CLOSED}
    → REJECT "订单已售后，不可重复退款"
```

这是防「一个订单退两次钱」的资损红线。

---

## 9. 回写闭环

退款通过后，`finalize_node` 在落 `RefundCase` 终态的同时，同步回写订单状态：

```
APPROVED → 同步 Order.status = REFUNDED（退款）/ 换货对应态
```

保证订单表与退款状态一致，同时支撑第 8 条防重复校验。

---

## 10. 商品快照（对账基准）

`OrderItem` 存的是**下单那一刻**的商品名 + 价格快照，而非实时商品。即使商品后续改名/改价/下架，售后对账仍以用户当时购买价格为准。

## 11. 图上下文存储（PG 主存 + Redis 快照，双写）

### 11.1 核心决策

- **PostgreSQL 主存**（最终真相，不丢）：`PostgresSaver` 照常落 checkpoint，挂起/resume 权威来源。
- **Redis 序列化快照**（加速 + 满足要求）：挂起时把 state 序列化成 JSON 存 Redis。

### 11.2 挂起时双写

```
挂起瞬间（human_review 的 interrupt 处）：
  state → json.dumps → SET refund:suspend:{case_id}  (TTL 7 天)
  同时 LangGraph 照常把 checkpoint 落 PostgreSQL
```

### 11.3 resume 时职责分离

| 层 | 职责 |
| --- | --- |
| PostgreSQL checkpoint | **权威恢复**（正确性，不丢） |
| Redis JSON 快照 | **读取/展示**（前端详情、批量审批导出、运维排查），不参与状态推进 |

### 11.4 为什么不用纯 Redis

挂起单可能躺数天，纯 Redis（无 AOF）一旦重启/故障即「失忆」，resume 找不到上下文，退赔流程断掉。退赔是资损敏感场景，宁可慢不能丢。

## 17. 验收标准

| 能力 | 验收红线 |
| --- | --- |
| 买家注册登录 | 手机号唯一，登录返回 BUYER token |
| 商品浏览 | 商品列表分页+搜索，详情正确，图片正常 |
| 购物车 | 未登录不可用；加购/改数量/删除正确 |
| 下单支付 | 下单锁定总额（快照），支付后状态 PAID |
| 订单真实性 | 伪造/不存在的订单号 100% 被 REJECT，不进后续决策 |
| 商品一致性 | 明细缺失的订单转人工，不自动放行 |
| 价格一致性 | 申报额 > 实付额 / 对账不平 转人工或 REJECT |
| 防重复退款 | 同一订单第二次售后被拦截 |
| 回写闭环 | 退款通过后订单状态与退款状态一致 |
| 挂起上下文 | 挂起单 state 能序列化到 Redis（JSON），resume 由 PG 权威恢复 |
| 三态体现 | 前端三态主线清晰，八态细节保留 |
| 兼容 | 原两大核心场景（超300元挂起 / 小额秒退）不回归 |
