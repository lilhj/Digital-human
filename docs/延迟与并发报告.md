# 延迟与并发报告

> 数据源：`agent_runs.duration_ms`（每个节点落一条执行轨迹）
> 采集时间：2026-09-23 · 全库 107 个案件 · 单机开发环境
> 复现命令：`cd backend && python -m scripts.latency_report [--limit N]`

---

## 一、延迟分两层：用户感知 vs 后台处理

| 层次 | 耗时 | 说明 |
|---|---|---|
| **用户感知延迟** | **毫秒级** | 提交售后接口只写 PG + XADD 入 Redis Streams 即返回 202，**不等待**工作流执行 |
| **后台处理延迟** | **P50 3.3s / 平均 9.9s** | 9 节点工作流异步执行，用户可在售后列表页查看进度 |

这是异步解耦架构的直接收益：**接口层不受处理耗时影响**，买家不会卡在提交按钮上。

---

## 二、各节点耗时（全库 107 案件）

按均值降序，瓶颈一眼可见：

| 节点 | 次数 | 均值 | P50 | P95 | 最大 |
|---|---:|---:|---:|---:|---:|
| **FRAUD**（风控+舆情 LLM） | 69 | **7.9s** | 8.9s | 11.0s | 54.2s |
| **EVIDENCE**（PaddleOCR + Qwen2.5-VL） | 69 | **6.2s** | 3.7s | 21.2s | 26.1s |
| INTENT（双层意图识别） | 74 | 884ms | **13ms** | 3.0s | 13.1s |
| INTAKE（受理+Critic+DLP） | 107 | 85ms | 73ms | 130ms | 608ms |
| FINALIZE（结算+退款） | 103 | 40ms | 14ms | 115ms | 139ms |
| ORDER_VERIFY（订单三查） | 59 | 28ms | 20ms | 62ms | 67ms |
| HUMAN_REVIEW（人工断点） | 146 | 24ms | 22ms | 48ms | 71ms |
| DECISION（决策） | 90 | 13ms | 12ms | 22ms | 26ms |
| SENTIMENT（舆情，零额外调用） | 69 | 0ms | 0ms | 0ms | 0ms |
| DLP（脱敏） | 77 | 0ms | 0ms | 0ms | 1ms |
| CRITIC（语义安检） | 77 | 0ms | 0ms | 1ms | 2ms |

**结论：耗时高度集中在两个节点**——FRAUD 与 EVIDENCE 合计占端到端 95% 以上，其余 9 个节点（纯规则 + DB 操作）合计不到 200ms。

### 两个瓶颈的成因

**① FRAUD（均值 7.9s）**
- `sample_size=3`：同一次评估发起 **3 次 LLM 调用取中位数**（抗单次打分波动），**当前为串行**
- 单次 LLM 调用约 2.5~3s → 累计 8~10s
- 最大值 54.2s：外部 LLM API（agicto.cn）超时重试所致

**② EVIDENCE（均值 6.2s，P95 21.2s）**
- PaddleOCR 本地推理：首次加载需编译算子约 37s（已做 `warmup()` 预热，之后约 1.3s/张）
- Qwen2.5-VL（本地 7B，8G VRAM）：首次推理约 15s，之后数秒
- **冷启动抖动是这个节点 P95 达 21.2s 的主因**

### 一个值得注意的分布特征

- **FRAUD**：P50(8.9s) > 均值(7.9s) —— 走 LLM 的单子集中在 9s 附近，另有部分单子命中规则/降级路径（0ms）把均值拉低，中位数因此落在 LLM 簇内
- **INTENT**：均值 884ms 但 **P50 仅 13ms** —— 规则层命中即出结果（零 LLM），只有口语化表述才调 LLM

这两处差异正是**双层漏斗 + 短路设计**的直接体现。

| 指标 | 数值 |
|---|---|
| 案件数 | 107 |
| **平均** | **9.9s** |
| **P50** | **3.3s** |
| **P95** | **30.5s** |

> **P50 3.3s 与平均 9.9s 的差距**：多数单子走短路路径快速出结果——安全网关拦截、订单三查失败、意图不明、换货诉求等会**跳过 OCR 与全部 LLM** 直接定论；只有走完整链路的单子才会到 10~30s。

## 四、并发处理

### 架构分层

```
生产者（FastAPI）          Redis Streams           消费者（Worker）
  写 PG 落 CREATED    →   Consumer Group      →   水平扩展多 Worker
  XADD 入队即返回 202      XACK 确认                消费名唯一
```

### 四道并发防线

| 机制 | 解决的问题 |
|---|---|
| **Redis Streams 解耦** | 突发流量进队列缓冲，接口不被打挂（削峰） |
| **Consumer Group + XACK** | 多 Worker 分工消费；重启不重复处理 |
| **PG 乐观锁（version）** | 同一案件被并发消费时仅一个推进成功，其余跳过 |
| **幂等键 + 分布式锁** | 批量审批不重复退款（资损红线） |

### 失败兜底

业务异常 → 重试流（`retry_count+1`，上限 3）→ 超限进**死信队列** + 案件标 `FAILED` 告警，不无限重投。

### 连接池

`pool_size=20 + max_overflow=20 + pool_pre_ping=True`，配合 `uvicorn --workers 4`（每进程独立连接池），避免 PG 连接成为瓶颈。

## 五、吞吐现状与优化方向

### 当前吞吐

| 场景 | 吞吐 |
|---|---|
| **单 Worker 串行消费** | **约 6.1 单/分钟**（基于平均 9.9s） |
| 多开 N 个 Worker | 近似线性 N 倍（架构已支持，消费名唯一即可） |

### 诚实结论

- **接口层抗并发**：异步解耦 + 队列缓冲，突发流量只表现为排队，不会崩
- **Worker 层会积压**：单进程串行消费是当前演示版的真实短板，流量上来队列长度会增长

### 优化路径（按收益排序）

| 优先级 | 措施 | 预期收益 |
|---|---|---|
| **P0** | **FRAUD 三次 LLM 采样并行化** | 该节点 7.9s → 约 3s，端到端砍掉近一半 |
| **P0** | **Worker 水平扩展** | 架构已支持，多开进程即线性提升吞吐 |
| **P1** | VL 模型常驻预热（OCR 已做） | 消除 EVIDENCE 的冷启动抖动（P95 21.2s 主因） |
| **P1** | 分级快慢通道 | 低风险小额单跳过 VL/LLM 直通，仅高风险走全链路 |
| **P2** | 结果缓存 | 同图/同描述重复请求复用判定结果 |

## 六、复现方式

```bash
cd backend
python -m scripts.latency_report              # 全库统计
python -m scripts.latency_report --limit 20   # 仅最近 20 个案件
```

脚本只读不写库，输出：各节点耗时（均值/P50/P95/最大）+ 端到端总耗时 + 状态分布 + 吞吐估算。
